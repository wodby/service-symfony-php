# Symfony on Wodby

What this service adds to the PHP service it is based on. Check it before adding database, secret, mailer, proxy or cache settings to the application.

## Variables the service sets

| Variable | Meaning |
| --- | --- |
| `APP_ENV` | `dev` in environments of type `dev`, `prod` in every other type (`prod`, `staging`, `test`, `feature`). An environment of type `test` is a deployed application, not Symfony's test environment. `APP_DEBUG` follows it unless it is set on the service. |
| `APP_SECRET` | A secret generated by Wodby for the service. Symfony reads it by itself. Do not generate or commit another one for production. |
| `SYMFONY_TRUSTED_PROXIES`, `SYMFONY_TRUSTED_HEADERS` | Trust the private addresses of Nginx and the cluster gateway, and their `X-Forwarded-For`, `-Proto` and `-Port` headers, so Symfony sees the client's address and HTTPS. Symfony 7.2 and newer read them by itself. |
| `PHP_FPM_USER` | `wodby`, the owner of the code, so PHP-FPM and console commands can both write `var/`. |

Real environment variables take precedence over the committed `.env` files. Keep `.env` in the repository with safe defaults only; never put production secrets in it.

## Linked services

In addition to the variables of the PHP service:

| Link | Variable |
| --- | --- |
| Database | `DATABASE_URL`, the whole connection as one URL, with credentials. It has no `serverVersion` and no `charset`. |
| Mail | `MAILER_DSN`, `smtp://<host>:<port>` of the linked mail service |

`DATABASE_URL` holds a password, percent-encoded: never print or commit its value, and read it with `%env(DATABASE_URL)%`, not `%env(resolve:DATABASE_URL)%`, which takes `%40` for a parameter reference. Doctrine detects the server version when it first connects. With DoctrineBundle, a URL without `charset` or `serverVersion` fails on PostgreSQL before connecting; the Wodby boilerplate sets `charset` from the URL's scheme for that reason.

When a managed database server has a CA certificate, the PHP service mounts it and sets `DB_SSL_CA` to its path. Doctrine does not read it by itself; the Wodby boilerplate adds it to the connection with a DBAL middleware.

Without a mail link `MAILER_DSN` is absent and the `.env` default applies.

## Build

The PHP service's Dockerfile copies the code into `/var/www/html`. The boilerplate's pipeline runs `composer install` with development packages, because an environment of type `dev` runs the same image with the dev bundles enabled. The runtime variables and the database are not available during the build: do not warm the `prod` cache there.

## After a deployment

`php bin/console doctrine:migrations:migrate --no-interaction --allow-no-migration` runs after every deployment of the service. The start command and the pipeline do not have to run migrations. The action fails when the application does not have Doctrine Migrations.

## Files and sessions

`var/` is in the container's file system and does not survive a restart: the cache is rebuilt, and file-based sessions are lost and are not shared between replicas. Store sessions in the database or a Redis-compatible service when the application runs more than one replica. The service has no files volume; add one to the stack for user uploads.

## Web server

Use it with the `php-nginx` service, whose document root defaults to `public`, Symfony's front controller directory.

## In a development workspace

- The PHP service's workspace applies: the checkout is served as it is on disk, and `composer install` runs during setup.
- Workspace deployments do not run post-deployment actions. Setup runs the migrations after installing dependencies when the application has Doctrine Migrations; run `php bin/console doctrine:migrations:migrate` yourself after adding one.
- With `APP_ENV=dev` Symfony rebuilds its container when configuration or code changes; run `php bin/console cache:clear` after changing environment variables.

## Check the result

- `php bin/console about` shows the environment, debug mode and the cache and log directories.
- `php bin/console dbal:run-sql 'SELECT 1'` shows whether the database link works.
- `php bin/console doctrine:migrations:status` shows the applied migrations.
- `php bin/console debug:dotenv` shows which `.env` files are loaded and which values come from the environment.
